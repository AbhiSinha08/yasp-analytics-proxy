YASP runtime architecture

The Gateway accepts Postgres / Redshift connections. Query context describes the request; data context describes its output. Application datasets supply shared mappings. Callbacks customize the query path while the engine owns execution and resource bounds.

Runtime components

Configurable Callback: Query context, query modification, source selection, cache eligibility, result processing, and Application dataset loading. Rust callbacks are compiled with the consuming app; trusted Python callbacks are supplied before startup.

Cache eligibility and replay
Configurable Callback — cache eligibility: it receives effective SQL, Query context and AST data context. Eligible hits replay raw rows and matching model sidecars; they do not call the source or decision model. Current Query context, source selection and result processing still run. Source grants are not rechecked on a hit until execution resumes after expiry. Query context values and callback versions are not automatically cache-key fields; source filtering must appear in effective SQL or the source scope.





Supporting mechanisms















Configurable Callback — Application dataset loader: it fetches configured files or app services before serving. The catalog adapter loads source schema before the Gateway accepts clients. Separate configured timers refresh Application datasets and schema catalog snapshots; refresh failure keeps the last good values.

Configurable Callback — backend selection: choose a target, login/role and compute class together. Login and compute class are independent choices within configured permissions: either example login can open a connection to either allowed class.

Each connection pool belongs to a target, login and compute instance. Source grants apply to the chosen login. If a is full, ordered overflow tries b in the same class with the same login; it does not change the selected role or class.


Connection lifecycle: reuse an idle connection or open one on demand → execute → reset and return it, or discard it if cleanup fails. Idle physical connections can be reclaimed; active work and cleanup keep their capacity reservations.


Planned: Round-robin/least-busy distribution and provider compute provisioning/suspension remain planned. Opening and closing source connections is implemented; provisioning or dissolving the compute machines is a separate lifecycle capability.










AST data context: local lineage analysis combines the effective SQL tree and schema catalog. It traces output aliases to source columns before source selection. The current schema catalog describes its configured discovery source, not an automatic union of all targets.


Model data context: after raw rows arrive, bounded column metadata/samples go to the configured decision-model endpoint. The response supplies per-column answers, probabilities and confidence. It is available for result processing, not for the same query’s earlier source selection.


Configurable settings: configure the endpoint, questions, sampling and failure behavior. Configurable Callback — result processing: it combines Query context with both data contexts. Scores are evidence, not permissions; unavailable classifications stay explicit. A raw cache hit uses matching model sidecars without retrying the model.
